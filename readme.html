Hopon Food Automation

Test automation across three real Hopon Food systems — a single run carries one order from a customer's phone through a restaurant's kitchen to a driver's app.

1Prerequisites

  • Java 17+
  • Maven 3.9+
  • Playwright's Chromium browser — installed once below, not a separate manual download
  • Real credentials: a restaurant-admin login and a driver-app bearer token (dev-environment test accounts, not invented)

No Docker, Node, or Python required for the tests themselves — Docker/ exists only for an optional containerized run (§9).

2Setup — one time

cd hopon-food-automation
cp TestData.properties.example TestData.properties

Edit TestData.properties (gitignored — never commit real values) and fill in:

# customer web app
base.url=https://dev-food.hoponbd.com

# restaurant admin portal
restaurant.admin.url=https://dev-foodadmin.hoponbd.com
restaurant.admin.email=<real email>
restaurant.admin.password=<real password>

# driver-app API (bearer token from a real logged-in driver session)
driver.api.base.url=http://dev-api.hoponbd.com
driver.auth.token=<real JWT>
driver.device.id=<any string>

Then build once and install the Playwright browser binary:

mvn clean install
mvn exec:java -Dexec.mainClass=com.microsoft.playwright.CLI -Dexec.args="install chromium"
Tip

Set headless=false in TestData.properties to watch the browser while a test runs — far easier to follow than reading a stack trace after the fact.

3Running a test

Every suite here runs the same way — build once, then run through init.TestRunner naming the suite XML. This is the one command to remember; only the -Dsuite= value changes:

mvn "-Dsuite=test-suites/<suite-file>.xml" "-Dexec.mainClass=init.TestRunner" "-Dexec.classpathScope=test" exec:java
PowerShell users

Quote every -D argument exactly as shown, all one line. An unquoted =, or a stray space around the colon in exec:java, makes Maven misread it as a lifecycle phase and fail with LifecyclePhaseNotFoundException.

4Validation flows — the bug-report suite

test-suites/validationFlows.xml (WebFunctionalTests/ValidationFlows/) is a separate suite of 10 negative-path tests, each built by reproducing a real reported issue live against the dev backend first, then locking the actual observed behavior into an assertion. Some assert correct behavior (a regression guard); a few assert the current confirmed bug on purpose — those are supposed to show as failures until the underlying product bug is fixed. Screenshot evidence for every one of them is saved to target/bug-evidence/ on every run (see §6).

mvn "-Dsuite=test-suites/validationFlows.xml" "-Dexec.mainClass=init.TestRunner" "-Dexec.classpathScope=test" exec:java
TestChecksExpected result
GpsOutsideServiceAreaTest Customer with GPS far outside Dhaka (Cox's Bazar) tries to order pass Correctly blocked with "Restaurant is unavailable"
RestaurantNotAcceptingOrdersTest Restaurant toggled "Not Accepting Orders" before the item is added, then checkout attempted fails on purpose Confirmed bug: order still places, zero warning shown
MenuItemNotAvailableTest Menu item toggled "Not Available" before being added, then checkout attempted fails on purpose Confirmed bug: order still places, zero warning shown
NoValidationMessageOnCheckoutTest Same as above but item added first, restaurant goes offline after (exact reported repro order) fails on purpose Same confirmed bug, different ordering
RestaurantCancelsOrderTest Restaurant (admin) cancels an order while the customer's tracking page is open and never reloaded pass Reaches the customer live (~8s, polling) with a clear banner; also documents a minor bug (stale "Cancel Order" button stays visible on an already-cancelled order)
CancelOrderModalBrokenTest Customer clicks their own "Cancel Order" button on the tracking page fails on purpose Confirmed bug: nothing happens at all; root cause captured from the browser console (a missing Lucide "Cancel" icon crashes the confirmation toast)
CartBadgeOnLocationChangeTest Customer changes delivery location (Gulshan → real Uttara coordinates) with an item already in cart pass Basket stays anchored/populated, clear "outside delivery zone" warning, checkout disables — did not reproduce the reported misplacement for this transition
RestaurantExtendPrepTimeTest Restaurant clicks "Need More Time" (+20 min) on a Preparing order pass Customer's delivery-time window updates accordingly (no separate "delayed" banner, just the shifted ETA)
DriverCancelBeforeAcceptTest Driver (not yet assigned) tries to cancel an order pass Correctly rejected, 400 "Invalid user"
DriverCancelAfterAcceptTest / DriverCancelAfterArrivedTest Driver cancels after Accepted / after Arrived pass Both correctly allowed, driver unassigned, order returns to the pool
Designed to fail

Four of these tests (RestaurantNotAcceptingOrdersTest, MenuItemNotAvailableTest, NoValidationMessageOnCheckoutTest, CancelOrderModalBrokenTest) fail on purpose — that failure is the bug report. Don't "fix" them by loosening the assertion; fix the product bug, then update the assertion to match the corrected behavior.

7Known flakiness — and why it self-heals

DataSource/riderlist.csv holds 350 test phone numbers, reused across every run. Under heavy same-session usage the dev backend's OTP step can occasionally time out (rate-limiting, or just a slow render of the OTP boxes) — CONFIRMED the login mechanics themselves are fine (a fresh manual run completes in well under half the default timeout), so this is transient, not a real bug.

Every @Test in EndToEnd / CustomerJourney / ValidationFlows uses utils.RetryAnalyzer — four retries, a fresh random phone each attempt — so this self-heals without you re-running anything. A Retrying '...' line in the output is normal.

8Recording real locators — Playwright Codegen

For any screen not yet covered:

mvn exec:java -Dexec.mainClass=com.microsoft.playwright.CLI -Dexec.args="codegen https://dev-food.hoponbd.com"

Copy the generated locators into the matching page-object methods.
